# T3 Code Architecture, Integration Surfaces & Protocol Research

## 1. Executive Summary

This document presents a comprehensive, clean-room architectural analysis of T3 Code (tested against server version `0.0.39-nightly` on Node.js/Windows). It covers T3's internal contracts, HTTP REST endpoints, WebSocket RPC protocol, authentication mechanisms, provider drivers, and integration boundaries for Orchlet.

### Key Finding: T3 Plugin SDK Status
- **Current State**: T3 does **not** currently expose a published or stabilized external Node.js/npm plugin SDK for third-party extensions.
- **Architectural Implication for Orchlet**: Orchlet must **not** attempt to load inside T3's internal process or rely on unpublished internal extension points. Instead, Orchlet operates as an **autonomous external control plane daemon** communicating with T3 via:
  1. T3's loopback **HTTP REST API** and **WebSocket RPC** interface.
  2. A bidirectional **MCP (Model Context Protocol)** bridge.
  3. Declarative **Skill and Slash Command registrations** (`SKILL.md` / `.agents/skills`).

## 2. Server Runtime & Service Discovery

T3 records its active server process state in the user's home data directory:
- Path: `~/.t3/userdata/server-runtime.json`
- Schema:
  ```json
  {
    "pid": 35952,
    "port": 3773,
    "host": "127.0.0.1",
    "protocol": "http",
    "updatedAt": "2026-09-06T15:00:00.000Z"
  }
  ```
- **Metadata Endpoint**: `GET /.well-known/t3/environment`
  - Returns `environmentId`, `label`, `platform` (`os`, `arch`), `serverVersion`, and a granular `capabilities` map:
    - `threadSettlement`, `threadAutoSettlement`, `threadSnooze`, `threadPinning`, `threadPullRequestLinking`, `attachmentUploads`, `usageLimitSources`, etc.

## 3. Authentication & Session Management

T3 enforces an Effect HTTP API authentication middleware (`EnvironmentAuthenticatedAuth`):
- **Auth Postures (`ServerAuthPolicy`)**:
  - `desktop-managed-local`: Trusted loopback handoff used by the desktop app shell.
  - `loopback-browser`: Standalone server for browser pairing on the local host.
  - `remote-reachable`: Environment reachable from other devices requiring explicit pairing.
  - `unsafe-no-auth`: Explicit test/escape hatch.
- **Session Introspection**: `GET /api/auth/session`
  - Returns `{ authenticated: boolean, auth: { policy, bootstrapMethods, sessionMethods, sessionCookieName } }`.
- **Token Exchange**: `POST /oauth/token`
  - Accepts grant type `urn:ietf:params:oauth:grant-type:token-exchange` and optional DPoP headers.
- **WebSocket Tickets**: `POST /api/auth/websocket-ticket`
  - Generates a short-lived single-use ticket for establishing authenticated WebSocket connections.
- **Pairing Links**: `POST /api/auth/pairing-token` and `GET /api/auth/pairing-links`.

## 4. Orchestration API & WebSocket RPC

T3's core orchestration contracts are defined in `@t3tools/contracts/orchestration`:

### 4.1 HTTP Orchestration Endpoints
- `GET /api/orchestration/snapshot`: Full system read model (`OrchestrationReadModel`), including projects and threads.
- `GET /api/orchestration/shell`: Lightweight shell snapshot (`OrchestrationShellSnapshot`) containing project summaries and active thread heads.
- `GET /api/orchestration/threads/:threadId`: Detailed thread state (`OrchestrationThreadDetailSnapshot`) with paginated turns (`turnLimit`, `beforeCursor`).
- `POST /api/orchestration/dispatch`: Primary command ingress. Accepts `ClientOrchestrationCommand` and returns `DispatchResult`.

### 4.2 WebSocket RPC Protocol (`ORCHESTRATION_WS_METHODS`)
T3 provides real-time streaming subscriptions over WebSocket:
- `orchestration.subscribeShell`: Streams `project-upserted`, `project-removed`, `thread-upserted`, and `thread-removed` events with sequence numbers (`afterSequence`).
- `orchestration.subscribeThread`: Streams live streaming tokens, tool activity events (`tone: info | tool | approval | error`), checkpoints, and turn completion.
- `orchestration.dispatchCommand`: Dispatches orchestration commands over socket.
- `orchestration.getFullThreadDiff` / `getTurnDiff`: Retrieves unified git diffs for a given turn or entire thread.

### 4.3 Command Schema Taxonomy (`ClientOrchestrationCommand`)
1. **Thread Lifecycle**:
   - `thread.create`: `{ threadId, projectId, title, modelSelection, runtimeMode, interactionMode, branch, worktreePath }`
   - `thread.turn.start`: Primary prompt dispatch:
     ```typescript
     {
       type: "thread.turn.start",
       commandId: CommandId,
       threadId: ThreadId,
       message: {
         messageId: MessageId,
         role: "user",
         text: string,
         attachments: ChatAttachment[]
       },
       modelSelection?: ModelSelection,
       runtimeMode: "full-access" | "approval-required" | "auto-accept-edits",
       interactionMode: "default" | "plan",
       bootstrap?: {
         createThread?: ThreadTurnStartBootstrapCreateThread,
         prepareWorktree?: ThreadTurnStartBootstrapPrepareWorktree,
         runSetupScript?: boolean
       }
     }
     ```
   - `thread.turn.interrupt`: Halts active generation/tool execution.
   - `thread.approval.respond`: Submits approval decision (`accept`, `acceptForSession`, `acceptAlways`, `decline`, `cancel`).
   - `thread.user-input.respond`: Answers interactive questions from agent.
   - `thread.settle` / `thread.auto-settle` / `thread.unsettle`: Marks thread settled or re-activates on user interaction.
   - `thread.snooze` / `thread.unsnooze`: Temporarily suspends thread from active inbox until wake time or external event.

## 5. Provider Drivers & Quota Ingestion

T3 manages AI agent backends via modular provider drivers in `apps/server/src/provider`:

1. **Antigravity Driver (`AntigravityDriver.ts`)**:
   - Spawns Antigravity ACP runtime (`antigravity-acp`) as a child process.
   - Communicates via Agent Control Protocol (`effect-acp/schema`) over stdio.
   - Manages personal OAuth credentials and Google Cloud project contexts.
2. **OpenCode Driver (`OpenCodeDriver.ts`)**:
   - Spawns local `opencode serve` CLI or connects to remote OpenCode daemon via HTTP.
   - Ingests configured custom models (e.g. OpenRouter Gemini/Claude routes).
3. **Codex Driver (`CodexDriver.ts`)**:
   - Connects to local Codex app server (`codex.exe`).
   - Interrogates subscription rate limits via JSON-RPC `account/rateLimits/read` and notification `account/rateLimits/updated`.
   - Normalizes usage into a 5-hour rolling burst window (`primary`, 300 mins) and a weekly pool (`secondary`, 10,080 mins).
4. **Claude Driver (`ClaudeDriver.ts`)**:
   - Wraps Claude Code CLI / Agent binary.

## 6. Integration Architecture for Orchlet

To achieve clean-room provider independence and robust interoperability without forking T3:
- **Adapter Package**: `@orchlet/t3-adapter`
- **Inbound Triggering from T3**:
  1. **MCP Tool Bridge**: Register Orchlet as an MCP server (`orchlet_orchestrate`, `orchlet_status`) within T3's tool/provider configuration.
  2. **Slash Command / Skill**: Expose `/orchlet <prompt>` via T3's skill convention (`SKILL.md`), dispatching the user goal to Orchlet's control plane daemon.
- **Outbound Execution via T3**:
  1. Orchlet connects as an authenticated client (`Authorization: Bearer <token>`) to `http://127.0.0.1:<port>`.
  2. Dispatches sub-tasks via `POST /api/orchestration/dispatch` (`thread.turn.start`).
  3. Monitors execution progress and tool activity via WebSocket `orchestration.subscribeThread`.
  4. Automatically responds to tool approvals (`thread.approval.respond`) based on Orchlet's configured sandbox policy.
